# UAC2 Specification and Development Guide

## 1. Roles and topology

USB Audio Class 2 is host/device oriented:

- macOS is the USB host;
- STM32F401 is the UAC2 device;
- CoreAudio owns USB scheduling;
- the application selects the STM32 playback device but does not write raw USB packets with libusb.

The initial target is playback-only. UAC2 can be bidirectional, but bidirectional compliance requires a real capture/IN terminal, IN isochronous endpoint, and capture clock/feedback behavior. A PCM5102A output device does not need a fake IN path.

## 2. Current fixed format

The first interoperable format is intentionally narrow:

```text
USB speed:       Full-Speed (12 Mb/s USB bus)
Sample rate:     48,000 Hz
Channels:        2
Subslot size:    2 bytes
Bit resolution:  16 bits
Payload:         signed little-endian PCM16 stereo
Endpoint:        isochronous OUT
Feedback:        explicit Full-Speed Q10.14 by default; optional implicit comparison build
```

At 48 kHz, the host sends approximately 48 stereo frames per 1 ms USB frame. Each normal packet is about 192 bytes, but 49-frame packets are valid and are 196 bytes. Receive buffers must therefore accommodate at least 196 bytes with alignment headroom.

## 3. AudioControl topology

The project uses the native Zephyr `device_next` UAC2 class and devicetree entities:

```text
Clock Source (internal programmable, fixed 48 kHz)
        |
USB Input Terminal (USB streaming, front-left/front-right)
        |
Output Terminal (headphones/speaker)
        |
AudioStreaming interface, alternate 0/1
```

The USB Input Terminal name means audio enters the device from the USB host. The PCM5102A is represented by the downstream output terminal. The UAC2 entity ID is derived by Zephyr from child order, so the callback terminal ID must be obtained with `UAC2_ENTITY_ID(DT_NODELABEL(...))`, never hard-coded from a guess.

## 4. Control negotiation

A compliant host normally performs a sequence similar to:

1. Standard USB enumeration.
2. Read configuration, IAD, AudioControl, Clock Source, Terminal, and Streaming descriptors.
3. Query Clock Source current/range values.
4. Set the selected sample rate if the clock is programmable.
5. Configure streaming controls.
6. Set the AudioStreaming interface to alternate setting 1.
7. Device reports terminal enabled through `terminal_update_cb`.
8. Device supplies receive buffers through `get_recv_buf`.
9. Host sends isochronous OUT payloads.
10. Device receives them in `data_recv_cb` and requeues buffers.

A device can enumerate successfully while still failing at steps 3-6. Therefore `bNumInterfaces`, VID/PID, and macOS System Report are not sufficient proof of audio interoperability.

## 5. Zephyr API contract

The native public API is in:

```text
include/zephyr/usb/class/usbd_uac2.h
```

The important callbacks are:

- `sof_cb`: bus SOF notification;
- `terminal_update_cb`: alternate setting/terminal enable state;
- `get_recv_buf`: aligned buffer supplied to USB stack;
- `data_recv_cb`: buffer returned after OUT data arrives;
- `buf_release_cb`: release callback when applicable;
- `feedback_cb`: explicit feedback value;
- `get_sample_rate`/`set_sample_rate`: required when multiple clock rates are advertised.

For the first target, advertise only 48 kHz. If multiple rates are advertised, implement both current-rate read and set-rate callbacks before testing Apple hosts.

The project must call `usbd_uac2_set_ops()` before enabling the device and register the UAC2 class in the configuration. The class-code triple should match Zephyr's official UAC2 sample:

```c
usbd_device_set_code_triple(ctx, USBD_SPEED_FS,
                            USB_BCC_MISCELLANEOUS, 0x02, 0x01);
```

## 6. Feedback and synchronization

The default `build-uac2-stm32` device uses explicit Full-Speed feedback. The feedback value is Q10.14:

```text
48 samples/SOF << 14
```

The `build-uac2-implicit` comparison target uses `boards/stm32f401rct6_uac2_implicit.overlay`; for an OUT stream Zephyr removes the explicit feedback endpoint in this mode. A wrong feedback mode can result in successful enumeration but unstable streaming, so explicit and implicit builds must be tested separately.

Hardware diagnostics showed that macOS read the explicit feedback callback only during initial negotiation in the tested setup. The remaining HSI/PLLI2S drift therefore cannot currently be corrected by continuously changing the explicit feedback value; see `uac2_pcm5102_macos_dev_log.md` for measurements and possible future host-side compensation.

The output device's physical audio clock is generated by STM32 I2S2/PLLI2S. For a first interoperability test, keep the UAC2 clock descriptor fixed at 48 kHz and observe actual OUT packet delivery before attempting clock recovery or multiple sample rates.

## 7. Buffer ownership

`get_recv_buf` returns a buffer owned by the USB stack until `data_recv_cb` is invoked. The callback must:

1. inspect the payload size;
2. account for packet/frame/checksum statistics;
3. copy or consume the PCM data;
4. return/release the buffer exactly once according to the Zephyr class contract;
5. never retain a USB-owned buffer after release.

The PCM5102A writer has a separate I2S TX slab. After `i2s_write()` succeeds, ownership of the TX slab block belongs to the I2S driver until DMA completion. The USB receive buffer and I2S TX block must not be treated as the same allocation.

## 8. Packet-to-I2S conversion

USB packets are not guaranteed to match the I2S application block size. The current PCM5102A writer consumes 128-frame interleaved float blocks and converts them to signed PCM16 for I2S. The UAC2 receiver should:

```text
USB PCM16 packet
    -> validate even stereo frame count
    -> convert to float
    -> append to pending frame buffer
    -> when 128 frames exist, call PCM writer
```

The local fallback and UAC2 callback must not call the I2S writer concurrently. Use one mutex or one producer queue.

## 9. macOS host behavior

The macOS application should:

- enumerate playback devices;
- select the STM32 device by exact/stable name or explicit ID;
- request PCM16, stereo, 48 kHz to match the descriptor;
- decode the source file to float internally;
- apply DSP internally;
- convert the final callback output to PCM16;
- let CoreAudio send UAC2 isochronous packets.

A running CoreAudio callback proves only that macOS is producing frames for the selected logical device. STM32 must independently prove payload arrival with `RX packets`, byte/frame counts, and first-packet sample logs.

## 10. Diagnostics map

```text
USB device absent
    -> clock, USB pins, VBUS, device controller, physical cable

USB device enumerates, no Audio MIDI output
    -> configuration/descriptors/class registration

Audio device visible, terminal not enabled
    -> Clock Source controls, format controls, alternate setting, feedback mode

terminal enabled, buffers requested, RX packets = 0
    -> host did not start OUT endpoint or endpoint/control negotiation still loops

RX packets > 0, out_delivered = 0
    -> packet aggregation or callback ownership bug

RX packets/out_delivered advance, no sound
    -> PCM format, I2S clock/underrun, PCM5102A wiring, Line Out, amplifier
```

## 11. Test sequence

### Protocol test before music

Use a deterministic PCM pattern rather than a music file:

- frame sequence number;
- left channel `0x1000 + n`;
- right channel `0xE000 - n`;
- known rolling checksum.

The macOS sender reports callback count and measured frame rate. STM32 reports packet count, bytes, frames, checksum, buffer rejection, and I2S block count. The checksum must match before acoustic testing.

### Audio test

Only after protocol test passes:

1. use a known-duration audio fixture;
2. request 48 kHz PCM16 stereo;
3. run PCM16 -> float -> PCM5102A writer;
4. verify no I2S `-EIO`, no slab starvation, and stable 128-frame block cadence;
5. verify PCM5102A `LINE OUT` into the amplifier.

### Hardware tools

- macOS Audio MIDI Setup: device format and stream visibility;
- `system_profiler SPUSBDataType`: USB enumeration;
- USART1: STM32 UAC2 counters (LCD is intentionally excluded from UAC2 builds);
- USB protocol analyzer/Wireshark capture where available: standard and class request sequence, `SET_INTERFACE alt=1`, feedback, and isochronous OUT packets.

## 12. Scope and limitations

- Playback only: no microphone/capture endpoint is implemented.
- The advertised audio format is fixed at PCM16 stereo 48 kHz.
- The default explicit-feedback build and optional implicit-feedback build are separate comparison targets.
- Current STM32F401 hardware uses HSI/PLLI2S and exhibits measurable clock drift; stable enumeration does not imply drift-free playback.
- UAC2 firmware uses USART1 diagnostics and intentionally excludes LCD/USB CDC.

## 13. Implementation status

The STM32 path is organized as `source -> DSP/plugin pipeline -> output`. `src/uac2/usb_uac2_device.c` owns descriptors/endpoints/packet conversion; `src/uac2/uac2_audio_stream.c` owns the asynchronous worker handoff, device startup, and statistics snapshot. PCM5102A is an output stage in `src/pcm5102/pcm5102a_audio.c` with its public API in `src/pcm5102/pcm5102a_audio.h`. Hardware enumeration and playback have been verified, but every regression test still requires `SET_INTERFACE alt=1`, nonzero OUT payload, checksum/frame accounting, stable `out_delivered`, and acoustic output.

The first valid target is playback-only. “UAC2 is bidirectional” describes the class capability, not a requirement that every playback device expose a capture endpoint. A separate bidirectional test must add a real IN terminal, capture source, IN endpoint, and appropriate feedback.

No UAC2 claim is complete until the host sends payload and the device validates it. Build success and USB System Report enumeration are necessary but insufficient.
